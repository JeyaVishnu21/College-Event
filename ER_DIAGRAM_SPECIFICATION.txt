================================================================================
CROWD EVENT MANAGEMENT SYSTEM - DATABASE SCHEMA & ER DIAGRAM SPECIFICATION
================================================================================
Database Name : crowd_event_db
Engine        : MySQL 8.x+ / MariaDB (InnoDB, utf8mb4)
Total Tables  : 7 (users, venues, fest, events, images, crowd_analyses, alerts)
Purpose       : Complete attribute specification, relationships, cardinalities,
                and ER diagram syntax for modeling the database.
================================================================================

--------------------------------------------------------------------------------
1. SUMMARY OF TABLES & THEIR PURPOSES
--------------------------------------------------------------------------------
1. users          : Stores system users across 2 roles (administrator, organizer).
2. venues         : Campus event venues with capacities managed by college administrator.
3. fest           : Groupings for multi-event festivals or celebrations (e.g., "Legacy 2K26").
4. events         : Event proposals, requested/approved schedules, assigned venues and series.
5. images         : Real-time CCTV / crowd monitoring images captured during live events.
6. crowd_analyses : AI/CSRNet model inference results and predicted headcount per image.
7. alerts         : Overcrowding safety breach notifications dispatched to administrator & organizers.

3. RELATIONSHIPS & CARDINALITY (FOR DRAWING ER DIAGRAM)
================================================================================

Relationship 1: users to events
---------------------------------
- Type        : One-to-Many (1 : N)
- Parent Table: users (PK: id)
- Child Table : events (FK: organizer_id)
- Notation    : User (1) ----< (0..N) Event
- Meaning     : One User (organizer) can organize zero, one, or many events.
                Each event must have exactly one organizer.
- Delete Rule : ON DELETE RESTRICT (Cannot delete a user who has active events).

Relationship 2: venues to events
---------------------------------
- Type        : One-to-Many (1 : N)
- Parent Table: venues (PK: id)
- Child Table : events (FK: venue_id)
- Notation    : Venue (1) ----< (0..N) Event
- Meaning     : One Venue can host zero, one, or multiple events over time.
                An event can be unassigned (venue_id IS NULL) while pending,
                or assigned to exactly one venue upon approval.
- Delete Rule : ON DELETE SET NULL.

Relationship 3: fest to events
---------------------------------------
- Type        : One-to-Many (1 : N)
- Parent Table: fest (PK: id)
- Child Table : events (FK: series_id)
- Notation    : Fest (1) ----< (0..N) Event
- Meaning     : A Fest can group zero, one, or many events.
                An individual standalone event may not belong to any series (series_id IS NULL).
- Delete Rule : ON DELETE SET NULL.

Relationship 4: events to images
---------------------------------
- Type        : One-to-Many (1 : N)
- Parent Table: events (PK: id)
- Child Table : images (FK: event_id)
- Notation    : Event (1) ----< (0..N) Image
- Meaning     : One event can have multiple surveillance images uploaded over its duration.
                Each uploaded image strictly belongs to exactly one event.
- Delete Rule : ON DELETE CASCADE (Deleting an event deletes all its uploaded images).

Relationship 5: images to crowd_analyses
-----------------------------------------
- Type        : One-to-One (1 : 1 or 1 : 0..1)
- Parent Table: images (PK: id)
- Child Table : crowd_analyses (FK: image_id, UNIQUE)
- Notation    : Image (1) ---- (0..1) CrowdAnalysis
- Meaning     : Each image has at most one crowd analysis record (image_id has a UNIQUE constraint).
                Each crowd analysis record belongs to exactly one image.
- Delete Rule : ON DELETE CASCADE (Deleting an image deletes its AI analysis result).

Relationship 6: events to alerts
---------------------------------
- Type        : One-to-Many (1 : N)
- Parent Table: events (PK: id)
- Child Table : alerts (FK: event_id)
- Notation    : Event (1) ----< (0..N) Alert
- Meaning     : An event can trigger zero, one, or multiple overcrowding alerts.
                Each alert belongs to exactly one event.
- Delete Rule : ON DELETE CASCADE.

Relationship 7: users to alerts
--------------------------------
- Type        : One-to-Many (1 : N)
- Parent Table: users (PK: id)
- Child Table : alerts (FK: user_id)
- Notation    : User (1) ----< (0..N) Alert
- Meaning     : A user (administrator or organizer) can receive zero, one, or multiple alerts.
                Each alert notification is addressed to exactly one recipient user.
- Delete Rule : ON DELETE CASCADE.

Relationship 8: crowd_analyses to alerts
-----------------------------------------
- Type        : One-to-Many (1 : N)
- Parent Table: crowd_analyses (PK: id)
- Child Table : alerts (FK: crowd_analysis_id)
- Notation    : CrowdAnalysis (1) ----< (0..N) Alert
- Meaning     : A single crowd analysis calculation that breaches safe capacity can
                generate alerts for multiple stakeholders (e.g., both administrator and organizer).
                If the analysis record is removed, the alert record retains its count log.
- Delete Rule : ON DELETE SET NULL.

--------------------------------------------------------------------------------
A. dbdiagram.io / DBML Syntax (Paste at https://dbdiagram.io)
--------------------------------------------------------------------------------

Table users {
  id int [pk, increment]
  name varchar(100) [not null]
  email varchar(150) [unique, not null]
  password_hash varchar(255) [not null]
  role varchar(20) [not null, note: 'administrator, organizer']
  created_at timestamp
  updated_at timestamp
}

Table venues {
  id int [pk, increment]
  name varchar(100) [not null]
  location varchar(255) [not null]
  capacity int [not null, default: 0]
  status varchar(20) [not null, default: 'available']
  created_at timestamp
  updated_at timestamp
}

Table fest {
  id int [pk, increment]
  name varchar(150) [not null]
  description text
  start_date date
  end_date date
  created_at timestamp
  updated_at timestamp
}

Table events {
  id int [pk, increment]
  organizer_id int [not null, ref: > users.id]
  event_name varchar(150) [not null]
  description text
  status varchar(20) [not null, default: 'pending']
  requested_date date [not null]
  requested_start_time time [not null]
  requested_end_time time [not null]
  approved_date date
  approved_start_time time
  approved_end_time time
  venue_id int [ref: > venues.id]
  series_id int [ref: > fest.id]
  category varchar(50) [default: 'General']
  rejection_reason varchar(255)
  created_at timestamp
  updated_at timestamp
}

Table images {
  id int [pk, increment]
  event_id int [not null, ref: > events.id]
  image_path varchar(255) [not null]
  uploaded_at timestamp
  processing_status varchar(20) [not null, default: 'pending']
  created_at timestamp
  updated_at timestamp
}

Table crowd_analyses {
  id int [pk, increment]
  image_id int [unique, not null, ref: - images.id]
  predicted_count int [not null]
  analysis_timestamp timestamp
  processing_status varchar(20) [not null, default: 'completed']
  model_name varchar(50) [not null, default: 'CSRNet']
  created_at timestamp
  updated_at timestamp
}

Table alerts {
  id int [pk, increment]
  event_id int [not null, ref: > events.id]
  user_id int [not null, ref: > users.id]
  crowd_analysis_id int [ref: > crowd_analyses.id]
  detected_count int [not null]
  threshold int [not null]
  message varchar(255) [not null]
  status varchar(20) [not null, default: 'unread']
  created_at timestamp
}
